## 2. Contrat (décisions de l'architecte)

1. **`OllamaTimeoutError(AIBackendError)`** dans `src/engines/ollama_engine.py` : sous-classe, donc tous les consommateurs qui attrapent `AIBackendError` continuent de fonctionner.
2. **Reconnaissance par type uniquement** : un `TimeoutError` directement, ou dans le `reason` **immédiat** d'une `URLError`. Aucune récursion dans les raisons imbriquées, aucune recherche dans le texte d'un message, pas de tuple avec `socket.timeout` (alias de `TimeoutError` à partir de Python 3.10 ; aucun prérequis global n'est annoncé et rien n'a été exécuté sous Python 3.10).
3. **Points de conversion** : l'ouverture (`urlopen`), la lecture normale de la réponse et la lecture du corps d'une `HTTPError`. L'exception d'origine est conservée comme cause (`raise … from <exception d'origine>`).
4. **Le reste est inchangé** : les autres erreurs de transport gardent le message « unreachable » et leur chaînage ; les exceptions qui sortent brutes de la lecture d'un corps d'erreur HTTP (autre `OSError`, `ValueError`, erreurs `http.client`) sortent comme **le même objet**. Les erreurs de protocole `http.client.*` ne sont pas touchées.
5. **Message exact** : `Communication with Ollama at {base_url} timed out (configured timeout: {timeout:g} s). The request did not complete; the server's state is unknown.` Il n'affirme ni qu'aucune réponse n'a été reçue (des en-têtes ou une partie du corps ont pu l'être), ni que le serveur est joignable ou que la génération se terminera.
6. **Constructeur** : défaut `30.0` et signature positionnelle `(base_url, timeout)` inchangés. **`OLLAMA_GENERATION_TIMEOUT = 120.0`** dans `src/ui/main_window.py`, passé **explicitement** à l'instance de l'assistant (`MainWindow.ollama_engine`).
7. **Découverte inchangée** : `SettingsPage` construit sa propre instance avec `OLLAMA_DISCOVERY_TIMEOUT = 5.0` ; son texte de statut ne change pas. La catégorie de dépassement est partagée avec `list_models()` (même `_request_json()`), l'interface de réglages attrapant `AIBackendError`.
8. **Politique, pas garantie** : 120 s est une valeur de politique acceptée. La documentation Python décrit un délai pour des opérations bloquantes, **pas une échéance globale de requête** : la valeur ne borne ni la durée totale d'un appel ni le temps pendant lequel le dialogue reste inutilisable, et **aucune annulation n'est ajoutée**. La durée d'attente possible n'est ni bornée ni mesurée par cette mission ; aucun maximum de 120 s n'est promis.
9. **Exclusions** : streaming, annulation, préchauffage, `keep_alive`, réglage utilisateur du délai, nouvelle dépendance, prérequis Python, Domain, migration de réglages, `ApplicationSettings`, `ai_backend.py`, `PromptAssistantManager`, worker, dialogue et leurs textes, `ComfyUIEngine`/`ForgeEngine`.
