## 1. Problème

`WorkspaceStorage.load()` renvoyait le contenu d'un `project.json` dont la racine est un objet sans contrôler le type de ses quatre collections de premier niveau (`images`, `models`, `workflows`, `characters`). `Workspace.from_dict()` les lisait par `data.get(clé) or []` puis itérait, sans contrôle du contenant. **Effets déduits de la lecture du code** (ce que le comparatif A a observé est précisé en section 10) :

- une valeur **fausse** (`{}`, `""`, `0`, `0.0`, `false`) est lue comme une collection vide, sans erreur ;
- une valeur **vraie non itérable** (`1`, `-1`, `1.5`, `true`) provoque une `TypeError` brute pendant `WorkspaceManager.open()`, que `MainWindow.open_project()` n'intercepte pas (seule `WorkspaceManagerError` l'est) ;
- une chaîne ou un objet **non vide** est parcouru : pour `models`, `workflows` et `characters`, les éléments non objets sont filtrés (collection vide ; les valeurs d'un objet sont ignorées) ; pour `images`, les entrées `str` héritées étant acceptées (`Image.list_from_data`), une chaîne produit une entrée `Image` en mémoire par caractère et un objet une entrée par clé ;
- un `save()` ultérieur réécrit tout `project.json` depuis le Domain (remplacement atomique, sans copie de l'ancien fichier).

La fréquence et l'origine de telles valeurs ne sont pas établies. Seuls `WorkspaceStorage.load()` et `save()` ont été trouvés construisant le chemin de `project.json` dans `src/` (recherche lexicale, non exhaustive).

## 2. Décisions de l'architecte

- **Périmètre** : les quatre collections de premier niveau. Clé absente ou valeur `null` : comportement actuel conservé (collection vide). Valeur liste : traitement actuel de ses éléments conservé (chemins d'images hérités, tolérance aux entrées mal typées). **Toute autre valeur présente est refusée**, sans utiliser la vérité logique (`{}`, `""`, `0`, `0.0`, `false` comme leurs variantes non vides).
- **Emplacement** : `WorkspaceStorage.load()`, après le contrôle de racine objet ; `WorkspaceStorageError` ; propagation existante par `WorkspaceManager` (`WorkspaceManagerError(str(exc))`). Aucune réparation, normalisation écrite, migration ni sauvegarde ; `save()` inchangé.
- **Plusieurs collections fautives** : seule la première, dans l'ordre fixe `images`, `models`, `workflows`, `characters`, est signalée, quel que soit l'ordre des clés dans le fichier.
- **Message, partout** : `<fichier> has a '<clé>' value that is not a list` (un seul enregistrement `ERROR`, aucune cause chaînée).
- **Exclus, risques restant ouverts** : collections imbriquées (`datasets`, `loras`, `prompts`, `trainings`), `settings`, `name`, `version` et tous les autres champs ; `RecursionError`, autres `ValueError`, fichier modifié pendant la lecture ; relecture de `onetrainer_config.json`.
- **Politique de validation, propre à Mission 179** : dérogation explicite à l'exigence de suite complète avant et après commit ; elle repose sur un comparatif ciblé et les voisins nécessaires, ne valide pas la suite complète, ne modifie pas `CLAUDE.md`, ne reconduit aucune autorisation de lancement de Mission 178 et n'autorise ni test ni commit. Le plantage `0xC0000374` de Mission 177 et les réserves Forge restent hors campagne. Pour mémoire : la dernière suite complète dont tous les tests ont réussi (Mission 176, 3 512 tests) a une supervision classée `OK_NON_NET`.
- **Documentation** : la correction datée de l'énoncé D2 de `MISSION_178.md` (section 7) sera intégrée à la consolidation documentaire de cette mission, dans le même commit ; elle ne modifie ni le tag ni la Release de Mission 178. **Elle a été appliquée le 2026-10-16, avec la consolidation documentaire de cette mission (section 11).**

## 3. Contrat et production (un seul fichier)

`src/infrastructure/storage/workspace_storage.py`, dans `WorkspaceStorage.load()` seulement (+17 lignes, 0 supprimée) : après `if not isinstance(data, dict): … raise`, pour chaque clé de `("images", "models", "workflows", "characters")` dans cet ordre, `value = data.get(clé)` ; si `value is not None and not isinstance(value, list)`, un `logger.error` puis `WorkspaceStorageError(f"{file} has a '{key}' value that is not a list")`. L'absence de la clé et `null` donnent tous deux `None` et sont acceptés. Rien n'est écrit, réparé ni renommé. `save()`, `WorkspaceManager`, le Domain, l'interface, `main.py` et les deux autres stockages sont **inchangés**.

## 4. Limites

- Seul le contenant est contrôlé ; les éléments d'une liste ne le sont pas (leur traitement par le Domain est inchangé et n'est pas figé par ces tests au niveau du stockage).
- Le texte de l'erreur s'affiche tel quel dans la boîte critique de `open_project` (anglais technique, avec le chemin) ; son rendu à l'écran n'est pas observé.
- Un `project.json` portant `{}`, `""`, `0` ou `false` pour une des quatre clés, aujourd'hui chargé comme collection vide, sera refusé : changement de comportement assumé. Aucun écrivain applicatif de ces formes n'a été trouvé (`Workspace.to_dict()` émet des listes) ; cela ne couvre pas un fichier produit autrement.
- Les gardes de brouillons de `open_project` s'exécutent avant l'ouverture : un brouillon abandonné avant une ouverture ensuite refusée est perdu (comportement préexistant pour toute erreur d'ouverture, hors périmètre).
- Les effets du code précédent décrits en section 1 sont déduits de la lecture. Le comparatif A (section 10) en a observé une partie : `TypeError` brute pour les quatre valeurs vraies non itérables, et absence d'exception pour les huit autres formes. Il n'a **pas** inspecté le contenu chargé (le test échoue avant) : la fabrication d'entrées `Image` pour `images` reste déduite de la lecture.
