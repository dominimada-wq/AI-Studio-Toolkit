# Mission 084 — Protect a Pending Generation Result Against Silent Loss on Workspace Context Change

> **MISSION ENTIÈREMENT CLOSE ET PUBLIÉE.** 35 tests ciblés nets nouveaux (11 sur `test_inference_page.py`, 7 sur `test_main_window_close_event.py`, 12 sur `test_main_window_new_project.py`, 5 sur `test_main_window_rename_project.py`, dont 1 adapté), suite complète 1552/1552, smoke test Qt réel exécuté et **PASS** (29/29 assertions — voir section 5). Commit fonctionnel `5cd63b018b3ded32a86462f41c923bfb9a59f685`, tag annoté `v0.2-mission084`, GitHub Release **publiée** — confirmée par l'architecte du projet. Voir section 7 pour l'état de clôture Git.

## 1. Contexte

L'audit post-Mission 083 a identifié qu'un résultat de génération terminé mais pas encore Accept/Reject (`InferencePage._pending_path`, un fichier réel déjà écrit sur disque dans `outputs/`) était détruit sans aucune confirmation dès que le contexte Workspace changeait — New Project, Open Project, fermeture de l'application, ou renommage du projet — même quand rien d'autre n'était dirty nulle part dans l'application. `InferencePage.reset_for_workspace_change()` (abonnée à `WORKSPACE_CREATED/OPENED/CLOSED/RENAMED`) appelait inconditionnellement `_clear_pending(delete_file=True)` sur chacun de ces 4 événements, sans jamais consulter aucun des 5 guards `confirm_context_change()` déjà établis, aucun desquels ne connaissait `_pending_path`. Confirmé empiriquement (22/23 assertions, script Qt réel) sur les 4 chemins UI accessibles, y compris les combinaisons pending seul, pending + prompt Inference dirty, et pending + une autre Page dirty.

## 2. Objectif

Protéger `_pending_path` par un choix explicite Accepter/Rejeter/Annuler avant toute transition qui le détruirait, sans fusionner ce mécanisme avec `confirm_context_change()` (état indépendant du texte du prompt), et sans dupliquer la logique Accept/Reject déjà établie par les boutons existants.

## 3. Mini-audit contractuel préalable

- **Réutilisation Accept/Reject** : `_on_accept_clicked()` contenait 3 branches distinctes — contexte Workspace périmé (avertissement, pending détruit), fichier disparu du disque (avertissement, pending détruit), échec réel de `WorkspaceManager.add_images()` (`WorkspaceManagerError`, erreur critique, **pending préservé**, seul chemin permettant un retry). `_on_reject_clicked()` : suppression physique inconditionnelle, avertissement best-effort seulement si la suppression échoue, jamais bloquant. Extraction de deux primitives privées à comportement byte-identique — `_accept_pending_result() -> bool` et `_reject_pending_result() -> None` — partagées entre les boutons existants et le nouveau guard, sans introduire d'abstraction générique inter-Page.
- **Distinction critique découverte pendant le mini-audit** : parmi les 3 issues d'échec d'`_accept_pending_result()`, seul l'échec réel de persistence (`WorkspaceManagerError`) préserve `_pending_path` (retry possible). Les deux autres (contexte périmé, fichier disparu) détruisent déjà le pending comme effet de bord de leur propre gestion actuelle — le guard doit donc laisser la transition continuer dans ces deux cas (rien à protéger), et la refuser uniquement sur un vrai échec de persistence. Validé explicitement par l'architecte avant implémentation.
- **Contrat retenu** : `confirm_pending_result_change() -> bool`, méthode strictement séparée de `confirm_context_change()` — les deux états (texte du prompt, résultat pending) restent indépendants, jamais mélangés dans une seule méthode/dialogue. Si aucun pending, retourne `True` immédiatement sans dialogue. `Cancel` → `False`, aucune modification. `Accept` → `_accept_pending_result()` ; succès → `True` ; échec avec `_pending_path` encore défini (persistence réellement échouée) → `False` ; échec avec `_pending_path` déjà `None` (contexte périmé/fichier disparu) → `True` (rien à protéger). `Reject` → `_reject_pending_result()` puis `True` (jamais bloquant, même si la suppression physique échoue).
- **Ordre des 6 guards** : `Prompts → Characters → LoRA → Settings → Inference prompt → Inference pending`, validé sans incohérence — séquence non transactionnelle entre guards (un Save/Accept déjà réussi n'est jamais rollback par un Cancel ultérieur), exactement le même principe déjà établi depuis les Missions 069/078/079/083 entre les 5 premiers guards.
- **Rename — vérification empirique obligatoire** : `rename_project()` n'appelait déjà aucun des 5 guards texte (cohérent : aucun `reset_for_context_change()` n'est abonné à `WORKSPACE_RENAMED` depuis M083) — seul le guard pending y est ajouté, après acceptation de `RenameProjectDialog` et avant `workspace_manager.rename()`. Vérification empirique réelle (16/16 assertions) : `WorkspaceManager.rename()`/`_build_renamed_payload()`/`_remap_path()` remappent déjà correctement `Workspace.images[].file_path` (contrat Mission 027/028, inchangé) ; le déplacement physique du dossier racine (`old_root.rename(new_root)`) déplace intrinsèquement le fichier accepté avec lui. Accept réel → Rename réel → fichier physiquement présent au nouveau chemin remappé, contenu intact, projet réouvert avec référence valide. **Aucune anomalie détectée.**
- **Interaction avec `reset_for_workspace_change()`** : son contrat reste **entièrement inchangé** (toujours 4 événements, toujours `_clear_pending(delete_file=True)` inconditionnel). Après un Accept/Reject réussi via le nouveau guard, `_pending_path` est déjà `None` avant que l'événement Workspace ne soit publié — la méthode devient un pur filet de sécurité inerte dans le flux normal, jamais un second point de décision concurrent. Vérifié par test qu'aucune double suppression ne se produit.
- **Dialogue UX** : trois boutons personnalisés (`addButton`, pas `Save/Discard/Cancel`) — « Accepter l'image » / « Rejeter l'image » / « Annuler » (défaut), reprenant le vocabulaire déjà visible sur la page, sans mentionner `_pending_path`.

## 4. Implémentation

**`InferencePage`** ([inference_page.py](../../src/ui/pages/inference_page.py)) :
- `_on_accept_clicked()`/`_on_reject_clicked()` réduits à de simples wrappers (`if self._pending_path is None: return` + délégation) autour des nouvelles primitives `_accept_pending_result() -> bool` et `_reject_pending_result() -> None`, corps byte-identiques aux anciens handlers — aucun changement de comportement pour les boutons existants.
- Nouvelle `confirm_pending_result_change() -> bool` : même contrat public `True`=proceed/`False`=abandon que `confirm_context_change()`, méthode et dialogue (`_confirm_pending_before_switch() -> str`, retournant `"accept"`/`"reject"`/`"cancel"`) strictement séparés.
- `reset_for_workspace_change()` : docstring étendue pour documenter la nouvelle relation filet-de-sécurité avec le guard — **aucun changement de comportement**.

**`MainWindow`** ([main_window.py](../../src/ui/main_window.py)) :
- `InferencePage.confirm_pending_result_change()` ajoutée en 6ᵉ et dernière position, après le guard Inference-texte existant, dans `new_project()`, `open_project()`, `closeEvent()` — `inference_page.shutdown()` reste appelé uniquement après résolution de tous les guards, sans déplacement nécessaire.
- `rename_project()` : **seul** le guard pending y est ajouté (aucun des 5 guards texte, cohérent avec M083 — un rename ne détruit aucun brouillon de texte), après acceptation de `RenameProjectDialog`, avant `workspace_manager.rename()`.

## 6. Conclusion

`InferencePage._pending_path` porte désormais le même principe de protection explicite que les 5 guards texte déjà établis (Missions 038/069/078/079/083), sans jamais fusionner les deux états indépendants (texte du prompt vs résultat de génération). Le mini-audit contractuel préalable a permis de distinguer, avant toute implémentation, un vrai échec de persistence (bloquant, retry possible) des deux cas où le pending est déjà détruit comme effet de bord de la primitive Accept existante (non bloquants, rien à protéger) — une nuance validée explicitement par l'architecte plutôt que décidée unilatéralement. La vérification empirique du remap de chemin lors d'un Accept suivi d'un Rename (16/16 puis 5/5 en test dédié) a confirmé qu'aucune anomalie ne remettait en cause le contrat Mission 027/028 existant. Aucun changement Domain/Manager/EventBus.
