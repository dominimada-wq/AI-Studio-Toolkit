# Mission 090 — Central LoRA Library Entry Editing (Name and Metadata)

> **MISSION IMPLÉMENTÉE, EN ATTENTE DE CLÔTURE GIT.** 33 tests ciblés nets nouveaux (10 `LoRALibraryManagerUpdateTest` + 23 `LoRAPageCentralLibraryTabTest`), non-régression complète, suite complète **1697/1697, aucun crash**, smoke test Qt réel exécuté et **PASS** (28/28 assertions, stable sur 3 exécutions consécutives — voir section 5). Voir section 7 pour l'état de clôture Git.

## 1. Contexte

L'audit post-Mission 089 a confirmé que l'onglet « Bibliothèque centrale » de `LoRAPage` permet désormais de consulter et supprimer une entrée, mais jamais de la corriger : `LoRALibraryManager` n'expose que `list_loras()`/`get()`/`import_lora()`/`delete()`, aucune méthode `update()`. Si le nom ou l'une des 4 métadonnées (`engine`/`architecture`/`trigger_word`/`version`) copiées à l'import (Mission 088) s'avère erronée, la seule solution est de supprimer l'entrée et de la réimporter depuis une LoRA Character-scoped source, ou d'éditer `lora_library.json` à la main — exactement la friction que Missions 087-089 ont déjà résolue pour la consultation/suppression.

Un mini-audit contractuel préalable, mené à partir du code réel, a fermé deux points avant toute écriture de code :

**Événement de mise à jour.** `LoRAManager.update()`/`update_name()` (Character-scoped, Missions 070/073) ne publient délibérément aucun événement — inutile, puisque `WorkspaceManager.save()` (appelé en interne) publie déjà `WORKSPACE_SAVED`, générique, auquel `LoRAPage.update_loras()` est abonnée (Mission 078) : le rafraîchissement de l'onglet Personnage est « gratuit ». `LoRALibraryManager` n'a aucun équivalent générique — son registre (`lora_library.json`) est un fichier de persistance séparé sans aucun signal de repli, raison exacte pour laquelle `import_lora()`/`delete()` ont chacun dû se doter d'un événement dédié. Un nouvel événement `LORA_LIBRARY_UPDATED` est donc réellement nécessaire (ni réutilisation détournée de `IMPORTED`/`DELETED`, ni absence d'événement).

**Dirty-state et changements de contexte.** `update_central_library()` n'est abonnée (mandat M089) qu'à `LORA_LIBRARY_IMPORTED`/`DELETED`, jamais à un événement Workspace/Character — un New/Open/Close/Rename de projet ne déclenche donc structurellement aucun reset de cet onglet, contrairement à l'onglet Personnage. Aucun guard n'est donc nécessaire sur `new_project()`/`open_project()`/`rename_project()` : rien n'y menace un brouillon central. Un risque réellement nouveau a en revanche été identifié : `update_central_library()` reconstruit aujourd'hui la liste et vide inconditionnellement le panneau de détail à chaque `LORA_LIBRARY_IMPORTED`/`DELETED` reçu — y compris pour une entrée totalement différente de celle en cours d'édition. Une fois le panneau éditable, cela détruirait silencieusement un brouillon sans rapport avec l'événement reçu. La fermeture complète de l'application (`MainWindow.closeEvent()`) reste par ailleurs une perte irréversible non protégée, comme pour tout autre brouillon de l'application.

## 2. Objectif

Permettre l'édition d'une entrée existante de la bibliothèque centrale — `name`, `engine`, `architecture`, `trigger_word`, `version` — depuis l'onglet « Bibliothèque centrale » de `LoRAPage`, avec les mêmes garanties transactionnelles et de protection de brouillon que le reste de l'application, sans jamais introduire le modèle de références/scopes Character/Workspace, l'exposition moteur/provider, l'import autonome depuis cet onglet, ou une migration de `project.json`.

## 3. Contrat final validé

### 3.1 `LoRALibraryManager` — nouvelle méthode `update()`

```python
def update(
    self,
    lora_id: str,
    name: Optional[str] = None,
    engine: Optional[str] = None,
    architecture: Optional[str] = None,
    trigger_word: Optional[str] = None,
    version: Optional[str] = None,
) -> bool:
```

Décision de conception (mini-audit) : **une seule méthode combinée**, et non le split `update()`/`update_name()` de `LoRAManager` — ce split est un artefact historique de deux missions distinctes (052 puis 073), pas un contrat à reproduire. Le précédent réellement applicable est `CharacterManager.update()` (Mission 074), qui mute `name` et les autres champs texte en une seule opération atomique : ici comme là, un seul formulaire, un seul bouton « Enregistrer », donc une seule mutation transactionnelle couvrant les 5 champs.

Contrat : `lora_id` inconnu → `False`, aucun `save()`. Idempotence stricte : `changed` est le OU logique des 5 comparaisons individuelles (`champ is not None and champ != valeur_actuelle`) ; si aucune n'est vraie → `False`, aucun `save()`, aucun événement. Chaîne vide légitime, distincte de `None`. Sur mutation réelle : capture des 5 anciennes valeurs, mutation, `self._save()` ; en cas d'échec (`LoRALibraryStorageError`), restauration exacte des 5 valeurs sur le même objet `LoRA` avant de lever `LoRALibraryError` (jamais `LoRALibraryStorageError` brute — même enveloppe que `import_lora()`/`delete()`). Sur succès : `self._publish(LORA_LIBRARY_UPDATED, lora)`, puis `return True`. `lora_id` (le champ, pas le paramètre) n'est jamais muté — seul `name`/`engine`/`architecture`/`trigger_word`/`version` le sont. Aucune opération filesystem : le dossier `<library_root>/<lora_id>/` est indexé par `lora_id` (uuid), jamais par `name` — confirmé par lecture directe d'`import_lora()`/`delete()` — un rename n'implique donc aucun déplacement de dossier.

### 3.2 Nouvel événement `LORA_LIBRARY_UPDATED`

Déclaré dans `src/managers/lora_library_manager.py` aux côtés de `LORA_LIBRARY_IMPORTED`/`LORA_LIBRARY_DELETED` (`LORA_LIBRARY_UPDATED = "lora_library.updated"`). Publié uniquement après un `_save()` réussi, jamais avant, jamais si `update()` retourne `False`. Payload : `lora.to_dict()`, même forme que les deux événements existants. `main_window.py` ajoute `LORA_LIBRARY_UPDATED` au tuple existant d'abonnement vers `lora_page.update_central_library` — aucun nouveau handler Presentation.

### 3.3 `update_central_library()` — garde de préservation du brouillon

Actuellement : reconstruction inconditionnelle de `library_list`, `_load_library_details(None)` systématique (sélection/panneau/bouton toujours vidés). Ce comportement reste correct pour `LORA_LIBRARY_IMPORTED`/`DELETED` concernant une **autre** entrée, mais doit devenir non-destructeur quand l'entrée actuellement chargée dans le panneau est encore dirty — mirroir exact de `update_loras()` (Mission 078) :

- Une nouvelle variable d'instance `self._loaded_library_lora_id` (mirroir de `_loaded_lora_id`) suit l'identité de l'entrée actuellement affichée dans le panneau, mise à jour par `on_library_selection_changed()` et par tout rechargement forcé.
- `library_list` est **toujours** entièrement reconstruite (lignes à jour, y compris un nom modifié).
- Le panneau de détail n'est rechargé (et le formulaire réinitialisé) **que si** `self._loaded_library_lora_id` ne correspond plus à une entrée existante **ou** si `self._library_metadata_dirty` est `False` — sinon, le panneau reste intact (le brouillon survit), et la ligne correspondante de la liste reconstruite est resélectionnée par identité (`blockSignals(True)` → `setCurrentItem(item, QItemSelectionModel.NoUpdate)` → `blockSignals(False)`, précédent Mission 082), sans réinvoquer `on_library_selection_changed()`.
- Cette même garde couvre naturellement le cas d'un `LORA_LIBRARY_UPDATED` auto-déclenché par la propre sauvegarde de l'utilisateur (voir 3.5) : au moment où l'événement est reçu, `_library_metadata_dirty` est encore `True` (remis à `False` seulement après le retour de l'appel Manager) — le panneau n'est donc pas rechargé inutilement, seule la ligne de liste reflète immédiatement le nouveau nom.
- Si l'entrée a disparu (supprimée par ce même utilisateur ou — structurellement impossible aujourd'hui, un seul onglet consommateur — par un autre chemin), la reconstruction redevient intégralement destructrice comme aujourd'hui : sélection/panneau/bouton vidés, `self._library_metadata_dirty = False`.

### 3.4 UI — formulaire d'édition

Le panneau lecture-seule de l'onglet central devient un formulaire éditable :
- Nouveau widget `library_name_edit` (`QLineEdit`) — le nom n'a aujourd'hui aucun widget dédié, seul le texte de l'item de liste l'affiche (combiné au nombre de fichiers) ; ajouté au panneau de détail, au-dessus des 4 champs existants.
- `library_engine_label`/`library_architecture_label`/`library_trigger_word_label`/`library_version_label` deviennent `library_engine_edit`/`library_architecture_edit`/`library_trigger_word_edit`/`library_version_edit` (`QLineEdit`).
- Nouveau bouton `save_library_metadata_button` (« Enregistrer »), nouvelle méthode `save_library_metadata()`.
- `_load_library_details()` peuple désormais les 5 `QLineEdit` (au lieu de `QLabel.setText()`), avec `blockSignals(True)`/`(False)` autour de la population programmatique (mirroir de `_load_metadata_fields()`), et réinitialise `self._library_metadata_dirty = False` à la fin — jamais quand elle est court-circuitée par la garde de préservation (3.3).
- `textChanged` des 5 champs → `self._library_metadata_dirty = True` (mirroir de `_on_metadata_changed()`), jamais déclenché pendant une population programmatique protégée par `blockSignals()`.
- **Bouton Enregistrer activé uniquement si `self._library_metadata_dirty` est `True` et qu'une sélection existe** — décision explicite, délibérément plus stricte que le précédent Personnage (`save_metadata_button`, activé dès qu'une LoRA est active, dirty ou non) : exigence exprimée directement par l'architecte pour M090, pas une régression de cohérence.
- `save_library_metadata()` : appelle `self.lora_library_manager.update(lora_id, name=..., engine=..., architecture=..., trigger_word=..., version=...)` ; sur `LoRALibraryError`, `QMessageBox.critical()` puis rechargement forcé du panneau depuis l'état persisté réel (`lora_library_manager.get(lora_id)`) — jamais un simple retour silencieux ; sur succès, `self._library_metadata_dirty = False` et réactivation/désactivation du bouton Enregistrer.

### 3.5 Dirty-state et guards

- `on_library_selection_changed()` gagne la même garde que `on_lora_selection_changed()` (Mission 078) : si `self._library_metadata_dirty`, affichage d'un dialogue Save/Discard/Cancel (`_confirm_discard_library_metadata_before_switch()`, mirroir exact de `_confirm_discard_metadata_before_switch()`) avant d'autoriser le changement de sélection ; Cancel restaure la sélection Qt précédente (`blockSignals`) sans rien persister ; Save appelle `update()` sur l'entrée quittée avant de continuer, avec le même traitement d'échec (`QMessageBox.critical`, sélection restaurée, changement annulé) ; Discard abandonne le brouillon sans persister.
- `delete_from_library()` : si l'entrée ciblée est celle actuellement chargée et dirty, le texte de confirmation est adapté pour mentionner la perte des modifications non enregistrées — mirroir exact de `delete_lora()` (Mission 078), pas de second dialogue.
- Nouvelle méthode `confirm_library_context_change() -> bool`, mirroir structurel de `confirm_context_change()` mais **branchée uniquement dans `MainWindow.closeEvent()`**, jamais dans `new_project()`/`open_project()`/`rename_project()` — rien de ce côté ne menace le brouillon central puisque l'onglet ne réagit à aucun de ces événements. Premier guard de ce type dans le projet à protéger un état purement Application-level plutôt que Workspace-level, mais avec le même mécanisme Save/Discard/Cancel que les 6 guards existants.
- Aucune notion de `active_lora_id`/sélection globale n'est introduite dans `LoRALibraryManager` — `self._loaded_library_lora_id` reste un état Presentation-only, exactement comme le mandat M089 l'exige déjà pour la sélection simple.

## 6. Conclusion

La bibliothèque centrale LoRA, consultable et supprimable depuis Mission 089, devient désormais éditable : `LoRAPage` permet de corriger le nom et les 4 métadonnées d'une entrée centrale directement depuis l'application, sans plus jamais nécessiter une suppression/réimport ou une édition manuelle de `lora_library.json`. `LoRALibraryManager.update()` applique les mêmes garanties transactionnelles que le reste du projet (idempotence stricte, rollback mémoire exact, événement publié uniquement après persistance réussie) via une seule mutation combinée, mirroir de `CharacterManager.update()` plutôt que du split historique `update()`/`update_name()` de `LoRAManager`. Le brouillon non enregistré est protégé sur tous les chemins de perte réels identifiés par le mini-audit — changement de sélection, suppression de l'entrée éditée, événement concernant une autre entrée, fermeture complète de l'application — sans jamais introduire de guard sur New/Open/Rename de Workspace, ceux-ci ne menaçant structurellement rien dans cet onglet Application-level. Aucune association Character/Workspace, aucun import depuis cet onglet, aucune exposition moteur/provider n'a été engagée — la fondation reste ouverte pour de futures missions dédiées.
