## 1. Contexte

L'audit post-Mission 086 a réévalué le besoin « Bibliothèque LoRA centralisée multi-engine », déjà enregistré et partiellement décidé lors de la régularisation de Mission 060 (`docs/PROJECT_CONTEXT.md`, décision A/B/C : stockage physique centralisé et unique, appartenance logique séparée du stockage physique, trois scopes `Character`/`Workspace`/`Global-Shared`, exposition moteur différée à un futur audit dédié).

Un premier mini-audit a confirmé, à partir du code réel (`src/domain/lora.py`, `src/managers/lora_manager.py`, `src/domain/character.py`) que :
- `LoRA` est aujourd'hui nichée dans `Character.loras`, sans collection top-level ni Manager Workspace-owned — un pattern d'ownership déjà atypique.
- `LoRA.files` ne sont **jamais copiés** physiquement (références externes brutes) — seul `LoRA.thumbnail` est physiquement possédé, sous `workspace_root/models/loras/<lora_id>/`.
- Aucune persistance hors Workspace n'existe dans ce dépôt, à une seule exception : `ApplicationSettingsStorage` (`%LOCALAPPDATA%\AIStudioToolkit\`), seul précédent réel pour un registre partagé entre projets.
- Deux systèmes « LoRA » déjà déconnectés coexistent : le catalogue riche `Character.loras` (jamais consommé par une génération) et `ApplicationSettings.comfyui_lora_name`/`comfyui_lora_strength` (seul réellement utilisé par `GenerationManager`, découvert côté serveur ComfyUI, sans lien avec `Character.loras`).

L'architecte a ensuite tranché quatre décisions structurantes (A — modèle Domain unifié, pas de type `SharedLoRA` parallèle ; B — suppression défensive, pas d'index global cross-Workspace ; C — grandfathering, aucune migration physique forcée des LoRA existantes ; D — stockage binaire configurable, jamais `%LOCALAPPDATA%` imposé), puis validé qu'une fondation minimale (registre + configuration du chemin), sans toucher à `Character.loras`/`LoRAManager`/`project.json`/l'UI existante/l'exposition moteur, est le périmètre correct pour Mission 087 — un champ Settings isolé sans registre associé ayant été explicitement écarté comme insuffisamment utile.

Un dernier mini-audit contractuel a fermé les questions de stockage restantes (emplacement exact du registre, réutilisation prudente de `WorkspaceStorage`, contrat précis du Manager, valeur par défaut du chemin binaire) et la politique de changement de chemin.

## 2. Objectif

Poser la fondation strictement minimale d'une bibliothèque LoRA centrale au niveau Application : un registre persistant, indépendant de tout Workspace, capable de posséder physiquement des fichiers LoRA (au lieu de les référencer), et un chemin de bibliothèque configurable dans les réglages de l'application — sans connecter cette fondation à quoi que ce soit d'existant.

## 3. Contrat final validé

### 3.1 Persistance du registre
- Nouveau fichier séparé : `%LOCALAPPDATA%\AIStudioToolkit\lora_library.json` — même répertoire qu'`ApplicationSettingsStorage` (résolu une seule fois au composition root via `ApplicationSettingsStorage.default_directory()`, injecté, jamais dupliqué), fichier distinct de `application_settings.json`.
- Schéma minimal : `{"loras": [LoRA.to_dict(), ...]}` — aucun champ de version (cohérent avec le reste du dépôt, qui ne connaît aucune convention de versioning explicite ; compatibilité assurée par `.get()`/filtrage `isinstance(x, dict)`, comme partout ailleurs).
- Fichier absent, JSON invalide ou non-dict → registre vide en mémoire, jamais d'exception (mirroir exact d'`ApplicationSettingsStorage.load()`).
- Écriture atomique : tempfile dans le même répertoire + `fsync` + `os.replace()` (mirroir exact d'`ApplicationSettingsStorage.save()`).
- Nouvelle classe `LoRALibraryStorage` (`load(directory)`/`save(directory, data)`), explicite et séparée — aucune abstraction Storage générique introduite.

### 3.2 Représentation Domain
- Réutilisation intégrale du dataclass `LoRA` existant (`src/domain/lora.py`), **aucun changement de code**, aucun type `SharedLoRA` parallèle.
- Distinction de **contrat**, pas de code : dans le registre central, `files` et `thumbnail` sont exclusivement des copies possédées par la bibliothèque (jamais une référence externe brute, contrairement au contrat actuel de `Character.loras`/`LoRAManager`) — à documenter explicitement dans le docstring du nouveau Manager.
- Plusieurs fichiers par LoRA conservés (`files: list[str]`, jamais réduit à une chaîne unique) — un fichier `.safetensors` principal plus d'éventuels fichiers auxiliaires restent représentables.
- Un dossier physique unique par `lora_id` (`<library_root>/<lora_id>/`) — élimine structurellement toute collision de nom de fichier entre deux entrées différentes.
- Identité stable : nouvel `uuid.uuid4()` à chaque import, jamais réutilisé. Deux imports du même fichier source produisent deux entrées distinctes avec deux copies physiques — **aucune déduplication par hash en M087**. Une collision de `lora_id` à la lecture (registre corrompu/édité à la main) est tolérée sans jamais rien supprimer silencieusement ; `get()` retourne la première correspondance.

### 3.3 Emplacement et politique du chemin binaire
- Valeur par défaut : `%USERPROFILE%\AI Studio Toolkit\LoRA Library\` — écarté `Documents` (synchronisation OneDrive automatique fréquente sur Windows 11, risque de consommation de quota cloud non désirée pour une bibliothèque de plusieurs Go) et `%LOCALAPPDATA%` (exclu explicitement par l'architecte).
- Création paresseuse du dossier (`mkdir(parents=True, exist_ok=True)`) au premier import réel — jamais de manière proactive.
- Nouveau champ `ApplicationSettings.lora_library_path: str` — jamais `Settings` Workspace-owned, une bibliothèque partagée entre projets ne peut pas se réinitialiser par Workspace.
- **Politique de changement de chemin (décision produit définitive)** : modifiable librement tant que le registre central est vide ; dès qu'il contient au moins une entrée, toute tentative de changement est refusée avec un message explicite ; supprimer toutes les entrées rend le chemin de nouveau modifiable ; aucune migration/copie/déplacement automatique n'est jamais tentée. Resaisir exactement la valeur déjà configurée reste un no-op autorisé même registre non vide (le refus ne se déclenche que si la valeur change réellement). Une future fonction explicite « Déplacer la bibliothèque » reste hors périmètre, à étudier séparément si un besoin réel apparaît.
- **Emplacement de l'invariant** : `ApplicationSettingsStorage.save()` n'est jamais appelé que depuis `ApplicationSettingsManager.update()` — c'est donc le seul point de passage réel, pas `SettingsPage`. `ApplicationSettingsManager` reçoit une référence optionnelle vers `LoRALibraryManager` (mirroir du pattern déjà établi : `LoRAManager` dépend déjà directement de `CharacterManager`/`WorkspaceManager`) et vérifie `lora_library_manager.list_loras()` avant de construire le candidat — refus via une nouvelle exception dédiée `LoRALibraryPathLockedError`, levée **avant** toute construction du candidat/tout appel à `save()`, garantissant que `self._settings` reste byte-for-byte inchangé après un refus (aucun rollback nécessaire, rien n'a été muté).

### 3.4 Champ Settings UI
- `ApplicationSettings`, jamais Workspace-owned `Settings`.
- Saisie libre + bouton « Parcourir » (`QFileDialog.getExistingDirectory()`) — extension mineure et cohérente du pattern déjà établi par `ModelsPage.browse_file()`.
- Validation à l'utilisation uniquement (mirroir exact d'`ApplicationSettingsStorage.save()`), jamais à la saisie.
- Chemin inaccessible/non inscriptible → erreur surfacée seulement au moment d'un import réel, via `QMessageBox.critical` (pattern déjà utilisé partout ailleurs) — jamais de crash.
- Refus de changement de chemin (registre non vide) → message explicite affiché à l'utilisateur, valeur précédente restaurée dans le champ.

### 3.5 `LoRALibraryManager`
Nom retenu — sans ambiguïté avec `LoRAManager` (Character-scoped, inchangé). API strictement minimale :

```
list_loras() -> list[LoRA]
get(lora_id: str) -> Optional[LoRA]
import_lora(name: str, file_paths: list[str], thumbnail_path: Optional[str] = None) -> LoRA
delete(lora_id: str) -> LoRALibraryDeletionResult
```

- **Pas de `select()`/`active_lora_id`** — aucune UI ne consomme le registre en M087, un concept de sélection courante n'aurait aucun consommateur.
- **`import_lora()` ne retourne jamais `None`** — vérifié contre le précédent réel `ModelManager.create()` (Workspace-owned, structurellement le plus proche) : celui-ci ne retourne `None` que pour une précondition externe légitime (`workspace_manager.current_workspace is None`), toute autre défaillance étant levée. `LoRALibraryManager` n'a aucune dépendance externe de ce type (Application-level, toujours constructible) — aucune précondition ne justifie `Optional`. Toute défaillance réelle (échec de copie, échec de persistence) lève une nouvelle exception contrôlée `LoRALibraryError`.
- **`get()` reste `Optional[LoRA]`** — une recherche par ID qui échoue est un cas normal, cohérent avec `CharacterManager`/`DatasetManager` et tout le reste du dépôt.
- `event_bus: Optional[EventBus] = None` conservé, cohérent avec les 13 autres Managers du dépôt — événements `lora_library.imported`/`lora_library.deleted`.

**Contrat transactionnel** (dès la création, pas de dette reproduite) :
- `import_lora()` : copie séquentielle de chaque fichier (+ thumbnail optionnel) dans `<library_root>/<lora_id>/` via `WorkspaceStorage.copy_into_workspace(source, destination_folder, workspace_root=destination_folder)` réutilisé (voir 3.6) — échec de copie = abandon avant toute mutation Domain, nettoyage best-effort du dossier partiel, aucune entrée créée. Construction du `LoRA`, ajout en mémoire, `LoRALibraryStorage.save()` — échec de sauvegarde = retrait de l'entrée en mémoire (mirroir `LoRAManager.create()`) + suppression best-effort de la copie physique désormais orpheline, erreur enrichie si ce nettoyage échoue aussi (mirroir `set_thumbnail()`). Succès → publication `lora_library.imported`, retour du `LoRA`.
- `delete()` : mirroir exact de `LoRAManager.delete()` (Missions 066/067/075) — dossier de l'entrée déplacé atomiquement vers `<library_root>/.trash/lora_<id>_<uuid>/` avant toute mutation Domain (abandon si ce déplacement échoue) ; retrait de la liste en mémoire ; sauvegarde du registre ; échec → réinsertion Domain (ne peut échouer) + tentative de déplacement retour du dossier, erreur enrichie en cas de double échec ; succès → suppression définitive best-effort du dossier de corbeille, `cleanup_failed`/`residual_path` rapportés sans jamais annuler une suppression déjà persistée. Publication `lora_library.deleted`. Ne touche jamais un fichier source externe (par construction : `import_lora()` ne fait que des copies, jamais de référence externe directe).

### 3.6 Primitives `WorkspaceStorage` réutilisées
Vérifiées fonction par fonction :
- `is_inside()`, `resolve_collision_free_name()`, `delete_folder()`, `rename_folder()` — génériques, déjà réutilisées ailleurs pour un usage non-Workspace (`.trash/` de Mission 075), réutilisables sans réserve.
- `copy_into_workspace()` — réutilisable **uniquement** en appelant `workspace_root=destination_folder` (la même valeur que `destination_folder`, jamais `library_root` entier) : le paramètre `workspace_root` ne sert qu'au test de passthrough « la source est-elle déjà dans ce périmètre » — l'appeler avec le périmètre entier de la bibliothèque romprait l'ownership strict par dossier d'entrée (une source déjà physiquement présente dans le dossier d'une **autre** entrée serait référencée sans copie, créant une dépendance physique cachée entre deux entrées). Aucune extraction de primitive neutre séparée n'est nécessaire pour M087 — la réutilisation précise suffit.

## 4. Implémentation

- `src/domain/application_settings.py` — nouveau champ `lora_library_path: str = field(default_factory=_default_lora_library_path)`, `_default_lora_library_path()` calculant `%USERPROFILE%\AI Studio Toolkit\LoRA Library` dynamiquement (`Path.home()`, jamais un littéral figé). `from_dict()` utilise `data.get("lora_library_path") or _default_lora_library_path()` — délibérément différent des autres champs `python_path`/`ollama_path` (`.get(clé, défaut)` simple) : un chemin de bibliothèque vide n'étant jamais un état exploitable, une chaîne vide explicite retombe elle aussi sur le défaut calculé.
- `src/managers/application_settings_manager.py` — nouveau paramètre `update(lora_library_path=...)`, nouvelle dépendance optionnelle constructeur `lora_library_manager: Optional[LoRALibraryManager] = None`, nouvelle exception `LoRALibraryPathLockedError`. Le verrou (`lora_library_path_changed` calculé isolément, vérifié via `lora_library_manager.list_loras()`, levé **avant** toute construction du candidat/tout appel à `save()`) est le seul point de passage réel de la persistence `ApplicationSettings` — `SettingsPage` ne peut pas le contourner.
- `src/infrastructure/storage/lora_library_storage.py` (nouveau) — `LoRALibraryStorage` : `default_directory()` délègue à `ApplicationSettingsStorage.default_directory()` (aucune logique de résolution dupliquée) ; `load()`/`save()` mirroir exact d'`ApplicationSettingsStorage` (écriture atomique, tolérance fichier absent/JSON invalide/non-dict) ; fichier séparé `lora_library.json`, même répertoire.
- `src/managers/lora_library_manager.py` (nouveau) — `LoRALibraryManager` : `list_loras() -> list[LoRA]`, `get(lora_id) -> Optional[LoRA]`, `import_lora(name, file_paths, library_root, thumbnail_path=None) -> LoRA` (jamais `Optional` — vérifié contre le précédent `ModelManager.create()`, aucune précondition Workspace/Character n'existe ici qui justifierait `None`), `delete(lora_id, library_root) -> LoRALibraryDeletionResult`. Aucun état de chemin conservé par le Manager — `library_root` est un paramètre explicite de chaque appel mutant, évitant toute dépendance circulaire avec `ApplicationSettingsManager` et tout risque de chemin périmé. Réutilisation précise de `WorkspaceStorage.copy_into_workspace()` avec `workspace_root=destination_folder` (jamais la racine entière de la bibliothèque) pour confiner le passthrough à cette seule entrée ; `is_inside()`/`resolve_collision_free_name()`/`delete_folder()`/`rename_folder()` réutilisées sans réserve. Contrat transactionnel : copie avant toute mutation Domain (abandon + nettoyage best-effort si une copie échoue, y compris partiellement) ; suppression via `.trash/` (mirroir Missions 066/067/075) ; `LoRALibraryError` normalise toute défaillance réelle, message enrichi si un nettoyage de secours échoue lui aussi.
- `src/ui/pages/settings_page.py` — nouveau champ `lora_library_path_edit` + bouton `lora_library_browse_button` (« Parcourir… », `QFileDialog.getExistingDirectory()`, mirroir du pattern déjà établi par `ModelsPage.browse_file()`), ajoutés à `application_form`. `save_application_settings()` capture `LoRALibraryPathLockedError` distinctement (message explicite + rechargement complet de la section via `update_application_settings()`, rétablissant la valeur réellement persistée). `update_application_settings()` affiche `settings.lora_library_path`.
- `src/ui/main_window.py` — `LoRALibraryManager` construit avant `ApplicationSettingsManager` et injecté dans celui-ci, sans dépendance circulaire.

**Hors périmètre, confirmé inchangé** : `Character.loras`, `LoRAManager`, `project.json`, toute UI `LoRAPage`/bibliothèque globale, association Character/Workspace, sélection Inference, exposition moteur (ComfyUI/Fooocus/A1111/Forge/providers cloud), déduplication par hash, migration ou copie automatique des LoRA déjà enregistrées.

## 6. Conclusion

La fondation Application-level de la bibliothèque LoRA centrale existe et fonctionne de façon autonome et transactionnelle dès sa création — aucune dette transactionnelle reproduite, chaque mutation (`import_lora()`/`delete()`) suit le même contrat éprouvé que `LoRAManager`/`DatasetManager` (abandon avant mutation Domain si le filesystem échoue, rollback complet si la persistence échoue, cleanup best-effort jamais bloquant après un succès déjà persisté). Le modèle Domain reste strictement unifié (`LoRA` réutilisé tel quel, aucun type parallèle), l'identité (`lora_id`) reste stable indépendamment de l'emplacement physique, et le verrou de changement de chemin vit au seul point de passage réel de la persistence (`ApplicationSettingsManager.update()`), impossible à contourner depuis `SettingsPage`. La bibliothèque reste fonctionnellement présente mais entièrement déconnectée de `Character.loras`/`LoRAManager`/`project.json`/Inference/tout moteur — exactement la fondation stable prévue pour Mission 088+, sans aucune migration ni décision d'exposition engagée prématurément.
