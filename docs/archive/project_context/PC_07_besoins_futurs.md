Ils ne constituent **aucune décision architecturale** — simple constat à évaluer par un futur audit :

- **`InferencePage` — images de référence : usages avancés (rôles/1..N réel/IP-Adapter/ControlNet)** : besoin réel qu'une génération puisse à terme utiliser plusieurs images d'entrée (1..N), potentiellement avec des rôles distincts selon le moteur/workflow retenu — cas illustratifs : portrait, planche de référence (character sheet), vêtement, décor, pose. **Trois briques posées** : Mission 021 a fourni le transport (`ComfyUIEngine.upload_image()`) ; Mission 022 a câblé ce transport à la verticale Inference réelle (collection `reference_images` 0..N dès la frontière applicative, snapshot défensif, fail-fast) ; Mission 023 a livré la **première consommation réelle** d'une référence unique via un workflow img2img natif ComfyUI (`LoadImage → VAEEncode → KSampler(denoise=0.75)`), validée par smoke test manuel réel. Le besoin avancé reste entier : aucune orchestration de rôle, aucun modèle ou nomenclature de rôles créé, aucune consommation réelle de plusieurs références simultanées (`>1` référence reste une erreur explicite par choix architectural, pas une limitation technique), aucun IP-Adapter/ControlNet — le mécanisme à retenir pour ces usages avancés reste un choix délibérément non engagé, à trancher par un futur audit dédié (voir `docs/missions/MISSION_023.md`, section "Perspective future"). **Mission 056 a posé la primitive structurelle nécessaire** : `Reference(path, role)` (`NamedTuple`, `src/managers/generation_manager.py`), collection `reference_images: List[Union[str, Reference]]` conçue pour 0..N, mais capacité de génération réellement livrée toujours strictement 0..1 référence actionnable — seul le rôle `REFERENCE_ROLE_POSE_COMPOSITION` existe comme constante, tout autre rôle (y compris les rôles futurs `identity`/`clothing`/`environment`/`style`, volontairement non déclarés en code pour éviter une taxonomie morte) est rejeté explicitement, toute collection de plus d'une référence est rejetée explicitement avant tout upload. Le besoin avancé reste donc entier au-delà de cette fondation : aucun mécanisme moteur réel (IP-Adapter/ControlNet/InstantID/PuLID) pour un second rôle, aucune consommation simultanée de plusieurs références — voir `docs/missions/MISSION_056.md`.
- **Envoyer un Dataset de références vers Inference (identifié après Mission 052, non implémenté)** : besoin futur distinct d'utiliser un Dataset comme bibliothèque persistante d'images de référence pour Inference — planche d'identité du personnage, portraits/références du personnage, vêtements, décor/environnement, pose/composition, autres références visuelles réutilisées fréquemment. Objectif utilisateur : éviter de devoir rechercher et sélectionner manuellement sur le disque les mêmes images de référence à chaque nouvelle génération. **Distinct de l'usage actuel d'un Dataset comme ensemble d'images destiné à l'entraînement d'une LoRA** — ne signifie notamment pas qu'un Dataset d'entraînement de 80 images doive pouvoir être injecté automatiquement en bloc dans Inference. Flux conceptuel envisagé : `DatasetsPage → sélectionner un Dataset → Envoyer vers Inference → sélectionner les références utiles → les utiliser comme entrées de génération`. Ce besoin doit rester cohérent avec le besoin architectural ci-dessus (`InferencePage` — images de référence : usages avancés, rôles/1..N réel/IP-Adapter/ControlNet) — exemples de rôles futurs possibles : `identity`, `face/portrait`, `clothing`, `environment`, `pose/composition`. **Non tranché, aucune implémentation** : reste à déterminer par un futur audit dédié — envoi du Dataset entier ou sélection de certaines images (et comment) ; nombre maximal de références accepté par Inference ; attribution éventuelle d'un rôle à chaque image ; comportement selon le moteur/workflow cible ; distinction UX éventuelle entre Dataset d'entraînement et Dataset utilisé comme bibliothèque de références ; interaction avec l'architecture future multi-références d'Inference (désormais dotée d'une primitive typée `Reference(path, role)` depuis Mission 056, mais dont la capacité de génération réellement livrée reste strictement 0..1 référence actionnable, `>1` restant une erreur explicite — voir le besoin ci-dessus) ; éventuelle réutilisation du sélecteur d'images introduit par Mission 044 (`SelectImagesDialog`) plutôt que création d'un nouveau composant. Aucun type Domain `ReferenceDataset`, aucun flag sur `Dataset`, aucun rôle persistant ni aucune nouvelle abstraction créés à ce jour — simple besoin enregistré, aucune mission créée. **Non résolu par Mission 056** : cette mission a posé la primitive typée nécessaire mais ne permet toujours pas d'envoyer plusieurs images d'un Dataset vers une génération — reste bloqué sur un premier mécanisme moteur réel pour un second rôle puis sur la consommation simultanée de plusieurs références, chacun nécessitant son propre audit dédié avant que cette intégration pratique devienne pertinente. **Toujours non résolu par Mission 057, Mission 058 ni Mission 059** — les trois missions sont restées hors périmètre Inference (nettoyage dead-code/documentation pour 057/058, sélection LoRA server-side pour 059) ; l'audit dédié de Mission 059 a explicitement reconfirmé ce statut inchangé (voir `docs/missions/MISSION_059.md`, section 9).
- **`InferencePage` — sélection du moteur/backend** : le besoin multi-engine (ComfyUI, Automatic1111, Fooocus, Forge...) est désormais un besoin utilisateur réel observé, plus seulement une anticipation du Blueprint — à prendre en compte lors des futurs audits Engine/Plugin. ComfyUI reste le seul Engine réellement implémenté et validé ; aucun autre Engine, `Plugin` ou `AI Orchestrator` n'est créé pour anticiper ce besoin. - **Sélection de LoRA multi-engine/multi-moteur (identifié Mission 022, non implémenté)** : besoin futur qu'un utilisateur puisse sélectionner un LoRA et l'utiliser avec les moteurs compatibles (ComfyUI, Fooocus, Automatic1111, Forge, futurs moteurs/IA cloud supportant les LoRA) — la conception future ne devra pas être couplée uniquement à ComfyUI. Distinction conceptuelle à respecter lors d'un futur audit : la **sélection/configuration** du LoRA (capacité générique côté Toolkit) est séparée du **chargement/application effective** du LoRA (adaptation spécifique au moteur/workflow/API). Aucune API, Domain model ou format de configuration n'est défini à ce jour — simple besoin enregistré, aucune mission créée. **Précision après Mission 047** : `LoRA.engine`/`.architecture` sont désormais réellement éditables (champs texte libres, aucune taxonomie fermée introduite) — ce besoin de sélection/configuration multi-engine reste néanmoins entièrement ouvert et non résolu par Mission 047, qui n'a traité que la consultation/édition des métadonnées, jamais leur exploitation pour piloter un choix de moteur. **Précision après Mission 059** : la sélection/application réelle d'une LoRA pendant une génération ComfyUI est désormais livrée (`ComfyUIEngine.list_loras()`, découverte server-side via `LoraLoader`, sélection Settings-level, force unique appliquée à `strength_model`/`strength_clip`, défaut `1.0`) — mais uniquement pour une LoRA **déjà connue du serveur ComfyUI actif**, jamais pour une entité `LoRA` du Workspace. **Nouvelle primitive manquante confirmée, non résolue par Mission 059** : `LoRA.files` contient des chemins externes bruts jamais copiés dans le Workspace (contrairement à `LoRA.thumbnail`, copié depuis Mission 047) — aucun mapping fiable n'existe entre une `LoRA` du Workspace et un `lora_name` reconnu par ComfyUI. Une stratégie reste à trancher par un futur audit dédié — copie/installation physique vers le dossier du moteur (nécessiterait de consommer `ApplicationSettings.comfyui_path`, toujours inexploité), enregistrement/déclaration auprès du moteur si un mécanisme existe, ou tout autre mécanisme fiable — **jamais une correspondance par simple nom de fichier (basename)**, explicitement exclue. Ce futur audit devra également tenir compte des champs `engine`/`architecture` déjà éditables depuis Mission 047. Voir `docs/missions/MISSION_059.md`, section 2 bis, pour l'audit complet de cette primitive manquante.
- **Bibliothèque LoRA centralisée multi-engine (identifié par l'architecte après régularisation de Mission 059, non implémenté)** : besoin architectural distinct du mapping LoRA Workspace↔moteur ci-dessus, mais lié — **ne pas réduire l'un à l'autre**, le mapping pouvant devenir une composante de cette future bibliothèque plutôt que s'y substituer. **Situation actuelle** : un même fichier LoRA peut devoir être installé séparément dans les répertoires propres de chaque moteur (ComfyUI, Automatic1111, Forge, Fooocus...), entraînant des duplications de fichiers `.safetensors` potentiellement volumineux — avec plusieurs moteurs et plusieurs LoRA, cette duplication peut consommer inutilement beaucoup d'espace disque. **Objectif futur** : AI Studio Toolkit devrait pouvoir devenir la bibliothèque/source centrale des fichiers LoRA, un même fichier physique devant, lorsque techniquement possible, être utilisable par plusieurs moteurs sans duplication ; les métadonnées déjà associées (`engine`, `architecture`, `trigger_word`, version, thumbnail) devront rester exploitables ; l'application devra savoir comment rendre une LoRA disponible à chaque moteur compatible. **Stratégies à auditer ultérieurement, aucune choisie à ce stade** : chemins de modèles supplémentaires configurables par le moteur, dossier partagé, configuration native du moteur, junctions/symlinks/hardlinks sous Windows lorsque pertinent, copie physique contrôlée uniquement lorsqu'un moteur ne permet pas de partager le fichier. **Contraintes à respecter par ce futur audit** : aucune duplication silencieuse ; aucune heuristique fragile basée uniquement sur le basename ; prise en compte de la compatibilité `engine`/`architecture` déjà éditable depuis Mission 047 ; ne pas supposer que ComfyUI, Automatic1111/Forge et Fooocus exposent les LoRA de la même manière — chaque moteur devra être audité avant de définir l'architecture définitive. Aucune API, Domain model ou mécanisme créé à ce jour — simple besoin enregistré, aucune mission créée, non concerné par Mission 060 (Adaptive Initial Window Size). **Décision architecturale retenue (validée par l'architecte pendant Mission 060, non implémentée, ne pas transformer automatiquement en Mission 061)** : principe désormais arrêté pour la future bibliothèque LoRA centralisée, le modèle de données et l'intégration moteur restant entièrement à auditer. Trois concepts distincts à ne jamais confondre dans une future implémentation : **(A) stockage physique** — un fichier LoRA physique unique autant que techniquement possible, bibliothèque gérée/centralisée par AI Studio Toolkit, aucune duplication automatique entre moteurs ou Workspaces (c'est le principe déjà couvert par ce besoin ci-dessus) ; **(B) appartenance logique** — un même fichier physiquement centralisé reste logiquement associable à un scope `Character` (LoRA d'identité, notamment), `Workspace` (LoRA spécifique à un projet) ou `Global/Shared` (LoRA réutilisable entre projets/personnages — peau, détail, réalisme, style, vêtements, etc.) ; **(C) exposition aux moteurs** — un futur audit dédié devra déterminer, moteur par moteur (ComfyUI, Automatic1111/Forge, Fooocus, etc.), comment consommer cette bibliothèque sans duplication (chemins configurables, dossier partagé, junctions/symlinks/hardlinks ou autre mécanisme approprié) — aucune solution technique choisie à ce stade. Contraintes supplémentaires retenues : distinction entre l'architecture du LoRA (`SD1.5`/`SDXL`/`FLUX`/etc.) et le simple format `.safetensors` ; compatibilité moteur/architecture à respecter ; possibilité future de rôles/tags (`identity`, `skin`, `detail`, `realism`, `style`, `clothing`, etc.), éventuellement multiples par LoRA ; métadonnées comme `engine`, `architecture`, `trigger_word`, version, thumbnail et fichiers à intégrer au futur modèle de données ; aucune heuristique fragile basée uniquement sur le nom de fichier ; aucune duplication volumineuse silencieuse. **Cette décision complète mais ne remplace pas** le besoin déjà enregistré ci-dessus (mapping LoRA Workspace ↔ moteur, concept C) — le mapping en devient une composante plutôt qu'un besoin autonome distinct.
- **Cache des vignettes / suppression des redécodages complets inutiles (identifié pendant l'audit de Mission 062, résolu par Mission 064)** : `src/ui/thumbnails.py::load_thumbnail_icon()`, consommé par `ImagesPage`/`DatasetsPage`/`SelectImagesDialog`, effectuait un décodage `QPixmap()` complet en pleine résolution suivi d'un redimensionnement, de façon synchrone sur le thread UI, sans aucun cache — chaque image était intégralement redécodée à chaque tri/sauvegarde/changement de contexte (Workspace/Character), même quand rien n'avait changé. Dette réelle et démontrée pendant le second audit exploratoire consécutif à Mission 061, explicitement écartée du périmètre de Mission 062 sur instruction de l'architecte (M062 = confirmation de suppression), puis résolue par Mission 064 via un cache LRU partagé et borné (`maxsize=256`, clé `(file_path, mtime_ns, file_size, width, height)`) — voir `docs/missions/MISSION_064.md`.
- **`PromptAssistantDialog` — Échap/fermeture pendant une génération active contournent le bouton Annuler désactivé (identifié pendant l'audit post-Mission 062, candidat B2, résolu par Mission 065)** : l'architecte a tranché l'arbitrage produit resté ouvert (Option A — interdire la fermeture pendant une génération, plutôt que l'autoriser en annulant proprement le résultat). Une vérification empirique préalable a confirmé que `reject()` est l'unique point de passage commun à Escape, à la fermeture native et au bouton Annuler ; Mission 065 y ajoute une garde unique réutilisant `cancel_button.isEnabled()` comme source de vérité busy/idle déjà existante — aucune nouvelle popup, aucun mécanisme d'annulation du worker/`QThread` introduit — voir `docs/missions/MISSION_065.md`.
- **Aléa d'environnement natif Qt/PySide6 (segfault en suite complète — priorité d'investigation depuis Mission 064, initialement observé pendant Mission 063)** : intermittent et de localisation non déterministe pendant Mission 063 (reproduit également sur le baseline sans son diff via `git stash`) ; devenu **reproductible à 5/5 exécutions complètes `unittest discover`** pendant Mission 064, systématiquement localisé dans `PromptAssistantDialogGenerateTest` (`tests/integration/test_prompt_assistant_dialog.py`, un vrai `QThread`/worker). **Investigation approfondie menée pendant l'audit post-Mission 064** : l'hypothèse initiale (tests ne laissant pas le temps au cleanup `QThread` de se terminer) a été **expérimentalement réfutée** par deux expériences ciblées, entièrement restaurées (attente explicite de `_thread is None` + `processEvents()` supplémentaire ; reproduction exacte du mécanisme `quit()+wait()` d'`InferencePage.shutdown()`) — le crash a persisté identiquement dans les deux cas. Le diagnostic `faulthandler` a révélé que le crash survient en réalité dans les internes CPython de `unittest.mock` (`NonCallableMock._lock` dans `__getattr__`), pas dans un chemin Qt/`QThread` — une reproduction isolée (500 cycles) et des exécutions groupées des deux modules réels (109/109, dans les deux ordres) ne l'ont jamais reproduit, suggérant une interaction liée au volume cumulé de la suite complète, non réductible à un cas isolé. **Ne s'est pas manifesté pendant les 3 exécutions complètes de validation de Mission 065 (1096/1096)** — aucune modification visant ce sujet n'a été apportée dans cette mission ; cette absence est une **observation de stabilité sur ces runs, pas une preuve de correction**. **Cause racine toujours non isolée** — une investigation native plus poussée (WinDbg/build de debug) serait disproportionnée à ce stade ; le sujet reste documenté comme anomalie technique connue, non isolée, sans mission dédiée tant qu'aucune nouvelle preuve concrète n'apparaît — voir `docs/missions/MISSION_064.md` section 9 et `docs/missions/MISSION_065.md` section 9. **Ne s'est pas manifesté pendant la validation de Mission 066 (1101/1101)** — toujours une observation de stabilité, aucune modification visant ce sujet apportée. **Ne s'est pas manifesté pendant la validation de Mission 067 (1121/1121)** — toujours une observation de stabilité, aucune modification visant ce sujet apportée. **Ne s'est pas manifesté pendant la validation de Mission 068 (1162/1162)** — toujours une observation de stabilité, aucune modification visant ce sujet apportée.
- **Publication sur réseaux sociaux (identifié Mission 022, non implémenté)** : besoin futur de permettre, après génération et validation d'une image ou d'une vidéo, sa publication sur des réseaux sociaux — choix du réseau, du compte (plusieurs comptes possibles par réseau), du média, d'une légende/texte, éventuellement hashtags/métadonnées, authentification requise par la plateforme, retour succès/erreur. L'authentification devra privilégier des mécanismes sécurisés (OAuth, tokens/API credentials, stockage sécurisé des secrets) — jamais de mot de passe en clair. Les erreurs externes (API indisponible, token expiré, authentification refusée, rate limit, changement d'API, publication refusée) devront être isolées : une panne d'une plateforme sociale ne doit jamais pouvoir affecter le cœur d'AI Studio Toolkit. **Décision architecturale volontairement non tranchée**, à comparer lors d'un futur audit dédié entre deux options — aucune des deux n'est présentée comme déjà choisie :
  - **Option A — intégrée** : page/module "Social Publishing" directement dans AI Studio Toolkit, isolé du cœur de génération.
  - **Option B — application indépendante** : application distincte dédiée à la publication sociale, recevant les médias générés par AI Studio Toolkit.

  Critères à comparer lors de ce futur audit : stabilité/robustesse du Toolkit, isolation des pannes, sécurité des comptes/tokens, dépendance aux SDK/API des réseaux sociaux et fréquence de leurs changements, maintenance, complexité, expérience utilisateur, gestion de plusieurs réseaux/comptes, transfert des médias et métadonnées, évolutivité indépendante. Aucune API, Domain model, dépendance ou page créée à ce jour — simple besoin enregistré, aucune mission créée.
- **`ComfyUI Installation Folder` — exploitation du champ `comfyui_path` déjà existant (identifié Mission 023, non implémenté)** : `ApplicationSettings.comfyui_path` (introduit Mission 010) **existe déjà** — visible et modifiable dans `SettingsPage` (champ `"ComfyUI :"`) — mais reste vide par défaut (`""`) et **n'est consommé par aucun code moteur à ce jour** (confirmé, `PROJECT_CONTEXT.md` section Infrastructure). Le besoin futur ne concerne donc pas la création d'un nouveau paramètre, mais **l'exploitation réelle de ce champ existant** : chemin local vers le dossier d'installation de ComfyUI, conceptuellement distinct de `comfyui_url` (`comfyui_url` sert la communication HTTP avec l'instance en cours d'exécution ; `comfyui_path` servirait la connaissance de l'arborescence locale) — détection automatique des checkpoints/LoRA/modèles ControlNet/adapters IP-Adapter installés, inspection de la présence de custom nodes requis par un workflow, ouverture directe des dossiers de modèles, vérification de compatibilité d'un workflow avec l'installation locale, éventuellement démarrage/arrêt de ComfyUI dans une mission ultérieure — utile également au futur système de sélection de LoRA déjà documenté ci-dessus. **Attention architecturale explicitement retenue** : ce champ devra vraisemblablement rester optionnel — une instance ComfyUI n'est pas nécessairement locale, et AI Studio Toolkit doit continuer à pouvoir communiquer avec ComfyUI uniquement via `comfyui_url` sans qu'un dossier d'installation local soit requis ou renseigné. Les cas ComfyUI local/portable/Desktop/instance distante/instance cloud restent à distinguer lors d'un futur audit dédié. **Sous-capacité « sélection du checkpoint ComfyUI » résolue par Mission 025 — mais indépendamment de `comfyui_path`.** L'approche initialement envisagée (`comfyui_path` → scan de `models/checkpoints/` → liste de checkpoints) a été **explicitement abandonnée avant implémentation**, suite à un audit read-only complémentaire ayant établi que l'installation réelle de l'architecte (ComfyUI Desktop pour Windows) démarre avec `--extra-model-paths-config .../shared_models.yaml` : les checkpoints réellement exposés peuvent provenir de chemins additionnels/partagés que Toolkit n'a aucune raison de vouloir résoudre lui-même (cela dupliquerait une résolution de chemins que ComfyUI fait déjà correctement en interne). Mission 025 interroge donc directement le serveur ComfyUI réellement en cours d'exécution via `GET {comfyui_url}/object_info/CheckpointLoaderSimple` (nouvelle méthode `ComfyUIEngine.list_checkpoints()`), plutôt que `comfyui_path`. `SettingsPage` expose désormais `ComfyUI Checkpoint` comme un `QComboBox` éditable (attribut `comfyui_checkpoint_name_edit` conservé), peuplé sur clic explicite du bouton "Rafraîchir les checkpoints" (jamais automatiquement), avec repli permanent sur la saisie manuelle si la découverte échoue (serveur injoignable, URL invalide, réponse inattendue) — validé par 370/370 tests automatisés et un smoke test manuel réel complet contre ComfyUI Desktop, y compris le cas de fallback. Voir `docs/missions/MISSION_025.md` pour le détail complet.

Un texte modifié manuellement dans l'éditeur mais non encore sauvegardé via « Enregistrer le texte » était donc perdu silencieusement si l'un de ces événements survenait pendant ce temps. **Comportement préexistant, antérieur à Mission 031/032, non introduit ni aggravé par le Prompt Assistant** — confirmé par lecture directe du code : `PromptsPage` ne possédait aucune notion de dirty-state, de confirmation avant perte, ni de sauvegarde automatique.   **Résolution effective par Mission 038** : un mini-audit UX dédié a distingué les causes de rafraîchissement plutôt que d'ajouter une confirmation uniforme, aboutissant à la solution **dirty-state local + refresh intelligent** — `self._dirty`/`self._loaded_prompt_id`, purement Presentation (`PromptsPage`), aucune modification de `Prompt`, `PromptManager`, du format Workspace ou de la persistance. `update_prompts()` ne recharge `text_edit` que lorsque `PromptManager.active_prompt_id` a réellement changé depuis le dernier chargement, préservant le brouillon pour les refresh non destructeurs (`WORKSPACE_SAVED`/`RENAMED`, `CHARACTER_CREATED`, `PROMPT_CREATED` sans sélection). Un changement volontaire de Prompt avec un brouillon dirty propose Enregistrer/Ignorer les modifications/Annuler — Annuler restaure réellement la sélection visuelle précédente sans jamais appeler `PromptManager.select()`, seul cas où une véritable annulation était possible. La suppression du Prompt dirty affiché est protégée de façon équivalente, sans notion de brouillon orphelin. Une séparation EventBus stricte, retenue après réexamen architectural explicite, confie `WORKSPACE_CREATED`/`OPENED`/`CLOSED` et `CHARACTER_SELECTED`/`DELETED` à une nouvelle `reset_for_context_change()`, gestionnaire unique et déterministe (aucune double souscription, aucune dépendance à l'ordre des abonnés EventBus). Validé par 696/696 tests automatisés et un smoke test manuel réel complet PASS — voir `docs/missions/MISSION_038.md`.
