
## Décisions techniques importantes à retenir

- Deux patterns d'ownership (Character-owned / Workspace-owned) + deux variantes singleton (Workspace-owned singleton `Settings` / Application-level singleton `ApplicationSettings`) + un pattern contextuel (`Image`, Mission 011, deux pools indépendants sans registre partagé) — voir `CLAUDE.md`.
- Aucune donnée Application (`ApplicationSettings`) n'est jamais stockée dans `project.json` ; aucune donnée Workspace (`Settings`) n'est jamais stockée dans `application_settings.json`. Aucune migration automatique entre les deux — jamais liées.
- Stratégie **"candidate-first"** pour `ApplicationSettingsManager.update()` : le nouvel état est construit et persisté avec succès *avant* tout remplacement de l'état mémoire (contrairement à `SettingsManager`, Mission 009, qui mute avant de sauvegarder — divergence assumée, non rétrofittée).
- Intégrité référentielle Dataset → Training : un Dataset référencé par ≥1 Training ne peut pas être supprimé, sans suppression en cascade.
- `TrainingPage` et `SettingsPage` sont les seules Pages du projet dépendant de deux Managers.
- Ownership `Training` : Character-owned avec un niveau de preuve Blueprint plus nuancé que `Model`/`Workflow` (ambiguïté `Training` vs `Training History` non résolue — voir dettes).
- **Migration `Image` (Mission 011)** — première migration du projet portant sur des données réellement présentes (contrairement à `Model`/`Workflow`, dont les champs équivalents n'avaient jamais contenu de données réelles) : `Image.list_from_data()` convertit `list[str]` (legacy) et `list[dict]` (nouveau format) de façon unifiée, partagée entre `Workspace.from_dict()` et `Dataset.from_dict()`. Un identifiant `uuid4()` est généré pour chaque entrée `str` legacy à chaque chargement tant qu'aucune sauvegarde n'a eu lieu ; il devient stable dès la première sauvegarde au nouveau format. Les doublons de chemin historiques sont préservés comme instances distinctes (aucune fusion, aucune perte).
- **Correction découverte en revue finale de Mission 011** : la première implémentation de `Image.list_from_data()` acceptait silencieusement des entrées `dict` sans `file_path` exploitable (ex. `{}`, `{"image_id": "abc"}` auraient produit une `Image` avec `file_path=""`). Corrigée avant commit : une entrée `dict` n'est conservée que si son `file_path` est un `str` non vide ; une entrée `str` legacy n'est conservée que si elle est non vide. Test de régression ajouté. Fait partie de l'historique technique réel de la mission, volontairement non effacé.
- **Frontière `AI Studio Toolkit → ComfyUI` (Mission 012)** : décidée après un audit dédié montrant que le protocole HTTP de ComfyUI (`/prompt`/`/history`/`/view`) ne distingue pas un node exécutant un modèle local d'un node appelant un service cloud (confirmé par l'existence de custom nodes communautaires type Gemini/Nano Banana s'intégrant au même protocole). `ComfyUIEngine` traite donc tout workflow comme un `dict` opaque — ses primitives génériques (`submit`/`wait_for_result`/`download_output`) ne connaissent ni checkpoint, ni modèle, ni provider. `Plugin`/`AI Orchestrator` volontairement non introduits : avec un seul moteur, ils seraient un pass-through sans logique réelle à porter.
- **Distinction Comfy Cloud API directe (Mission 012)** : Mission 012 implémente le protocole d'une instance serveur ComfyUI (locale ou distante), pas un client direct vers une éventuelle API "Comfy Cloud" hébergée (endpoints/authentification propres, potentiellement différents). Cette distinction est documentée explicitement pour éviter toute fausse promesse architecturale future.
- **Correction découverte en revue finale de Mission 012** : la première implémentation de `wait_for_result()` considérait comme terminé tout `outputs` non vide, sans vérifier qu'une image exploitable y figurait ; `_first_image_reference()` acceptait une référence sans `filename`. Corrigées avant commit : `wait_for_result()` continue le polling jusqu'à l'apparition d'une référence image structurellement exploitable (ou timeout) ; `_first_image_reference()` exige un `filename` non vide. 7 tests ajoutés. Fait partie de l'historique technique réel de la mission, volontairement non effacé.
- **Premier threading Qt du projet (Mission 013)** : idiome standard `QObject` (`GenerationWorker`) déplacé dans un `QThread` via `moveToThread()`. `GenerationManager` reste strictement Qt-free — le worker est la seule classe à connaître à la fois Qt et le Manager. `WorkspaceManager.add_images()` est appelé depuis le thread principal (slot connecté au signal `finished`), jamais depuis le worker, car `Workspace`/`WorkspaceManager` ne sont pas thread-safe.
- **Correction découverte en revue finale de Mission 013 — condition de course QThread** : `_cleanup_thread()` relisait `self._worker`/`self._thread` au moment de son exécution différée (postérieure à la réactivation du bouton) ; une génération relancée dans cette fenêtre pouvait faire détruire/réinitialiser par l'ancien cycle les références du nouveau cycle en cours. Corrigée avant clôture : `worker`/`thread` capturés par valeur dans le callback de cleanup, remise à `None` de `self._worker`/`self._thread` conditionnée à ce qu'ils pointent encore vers ce cycle précis. 4 tests ajoutés (dont 2 avec de vrais `QThread` et reclic immédiat, capturant tout message Qt via `qInstallMessageHandler`). Fait partie de l'historique technique réel de la mission, volontairement non effacé.
- **Limite shutdown Mission 013** : `thread.quit()+wait()` ne constitue pas une annulation — un appel `ComfyUIEngine` déjà en cours (le worker n'a pas encore atteint sa propre boucle d'événements) ne peut être interrompu ; la fermeture de l'application peut donc attendre jusqu'au timeout interne de `ComfyUIEngine` (120 s par défaut). Limite acceptée et documentée, non résolue, non testée empiriquement pendant les smoke tests réels (Mission 013 et Mission 014). **Conséquence pratique sur Close atténuée par Mission 085** (voir « Dette résolue par Mission 085 » ci-dessous) : `MainWindow.closeEvent()` refuse désormais immédiatement la fermeture tant qu'une génération est réellement active (`InferencePage.is_generation_active()`), donc `shutdown()` n'est plus jamais atteint dans ce cas et ne peut plus bloquer l'utilisateur jusqu'à 120 s ; la limitation technique elle-même (aucune annulation réelle du worker) reste entièrement inchangée — seule la fermeture pendant une génération active en est protégée, pas la génération elle-même.
- **Validation post-génération (Mission 014)** : `InferencePage` mémorise un état `pending` transitoire (chemin du fichier téléchargé, jamais persisté avant Accept) et le Workspace actif au lancement de la génération (`_generation_workspace_root`). Aucun nouveau Domain/Manager — `GenerationManager`/`GenerationWorker`/`ComfyUIEngine` strictement inchangés. Aucun nouveau canal EventBus.
- **Correction découverte en revue finale de Mission 014 — liaison pending/Workspace manquante** : ni le passage en pending ni Accept ne vérifiaient que le Workspace actif correspondait à celui actif au lancement de la génération ; `WorkspaceManager.create()`/`.open()` remplacent `current_workspace` sans jamais appeler `close()`, ce qui aurait permis en théorie qu'un résultat né dans un Workspace A soit enregistré dans un Workspace B ouvert entre-temps. Corrigée avant clôture : mémorisation de la racine du Workspace au lancement, vérification à l'arrivée du résultat et à Accept, invalidation proactive du pending via `InferencePage.reset_for_workspace_change()` abonnée par `main_window.py` à `WORKSPACE_CREATED`/`WORKSPACE_OPENED`/`WORKSPACE_CLOSED` (jamais `WORKSPACE_SAVED`). Vérifiée par tests automatisés dédiés et par le scénario E du smoke test réel. Fait partie de l'historique technique réel de la mission, volontairement non effacé.
- **Aperçu agrandi partagé (Mission 015)** : `ImagePreviewDialog` reçoit uniquement un `file_path` (`str`) — jamais une référence Domain/Manager/Page — garantissant structurellement (absence de canal, pas un garde-fou ajouté après coup) qu'il ne peut jamais modifier `Workspace.images`, un état pending, ni déclencher `WORKSPACE_SAVED`. Modal (`exec()`), ce qui empêche également toute action Accept/Reject/Regenerate/Generate pendant la consultation. Bouton plein écran et raccourci `F11` connectés au même callback (`_toggle_fullscreen()`) — un seul mécanisme.
- **Correction découverte en revue finale de Mission 015 — `QLabel.minimumSizeHint()` calé sur le pixmap affiché** : `_update_scaled_pixmap()` réassignait un nouveau pixmap redimensionné à chaque `resizeEvent`/`showEvent` via `setPixmap()`, ce qui faisait remonter silencieusement le plancher de taille minimale du `QLabel` — et donc de la fenêtre — à chaque agrandissement, empêchant ensuite tout rétrécissement en dessous de la plus grande taille déjà rendue. Reproduit empiriquement (script de sondage Qt réel, mesures de géométrie avant/après) puis corrigé avant clôture par `self.image_label.setMinimumSize(1, 1)`, qui découple explicitement la contrainte de layout du pixmap courant. Test de régression ajouté (`test_window_can_shrink_back_after_displaying_a_large_scaled_image`), revalidé pendant le smoke test réel par un cycle manuel agrandissement → fort rétrécissement → réagrandissement via le mécanisme système Windows (le glisser-déposer synthétique de bordure s'étant révélé peu fiable dans l'outil d'automatisation du smoke test lui-même, sans rapport avec un défaut d'AI Studio Toolkit). Fait partie de l'historique technique réel de la mission, volontairement non effacé.
- **Création directe de dossier de projet (Mission 016)** : `WorkspaceStorage.create_directories()` faisait déjà `Path.mkdir(parents=True, exist_ok=True)` avant cette mission — la capacité de créer un dossier inexistant existait déjà dans `WorkspaceManager`/`WorkspaceStorage`, seule l'UI (`QFileDialog.getExistingDirectory()` forçant un dossier déjà existant) empêchait de l'exploiter. `NewProjectDialog` construit et valide uniquement `target_path` ; il ne crée jamais rien lui-même sur le disque — la création physique reste exclusivement `WorkspaceManager.create()` → `WorkspaceStorage.create_directories()`, appelée par `MainWindow.new_project()` seulement après acceptation. `target_path` n'est jamais assigné avant l'acceptation (revalidation continue via `_revalidate()` sur chaque changement de champ), garantissant structurellement qu'aucune ancienne cible devenue invalide ne peut survivre à un état invalide.
- **Revalidation de collision à l'instant exact de l'acceptation (Mission 016)** : une collision peut apparaître sur le disque entre la dernière frappe/sélection et le clic sur "Créer" (course filesystem). `_on_accept_clicked()` recalcule systématiquement `_compute_target_path()` avant tout appel à `self.accept()` — si le chemin cible existe désormais, le dialogue reste ouvert, "Créer" se désactive, le message de collision s'affiche, et `WorkspaceManager.create()` n'est jamais atteint. Comportement reproduit et vérifié à la fois par test automatisé et manuellement en conditions réelles (dossier créé via un processus externe pendant que le dialogue restait ouvert).
- **Câblage des actions Dashboard (Mission 017)** : câblage effectué exclusivement dans `MainWindow` (composition root), jamais dans `DashboardPage` — `dashboard_page.newProjectButton.clicked.connect(self.new_project)`, `.openProjectButton` → `self.open_project`, `.importImagesButton` → `self.images_page.import_images` directement (aucune méthode intermédiaire, `ImagesPage.import_images()` étant déjà un point d'entrée public autonome). `trainingButton` désactivé + tooltip appliqués directement dans `DashboardPage.__init__` (configuration Qt pure, sans dépendance externe) plutôt que dans `MainWindow`, puisqu'aucune orchestration n'est nécessaire pour un bouton qui ne déclenche jamais rien.
- **Source de vérité unique pour la configuration ComfyUI (Mission 018)** : décision explicitement révisée en cours de spécification — une première approche (défauts Domain à `""` + constantes de repli dans `main_window.py`) a été écartée par l'architecte car elle aurait créé deux niveaux de configuration, avec des champs `SettingsPage` vides alors que l'application utilisait réellement des valeurs implicites ailleurs. Retenu à la place : `comfyui_url`/`comfyui_checkpoint_name` portent directement, comme valeur par défaut du dataclass `ApplicationSettings`, les valeurs auparavant codées en dur — une exception assumée au principe "`""` = non configuré" appliqué à tous les autres champs `ApplicationSettings`/`Settings`, justifiée parce que ces deux champs ont déjà un comportement fonctionnel réel et actif. `MainWindow` ne conserve aucun repli propre : il lit et transmet telles quelles les valeurs d'`ApplicationSettings`.
- **`Qt.UserRole` comme donnée fiable découplée de la présentation (Mission 019)** : `ImagesPage` utilisait `item.text()` à la fois comme label visible et comme unique source du `file_path`, empêchant toute évolution du texte affiché sans casser le comportement (double-clic, bouton "Voir en grand"). Retenu : `Qt.UserRole` porte désormais le `file_path` complet, seule donnée lue par les actions UI ; `item.text()` devient un pur label de présentation (nom de fichier court), sans plus aucune valeur fonctionnelle. Conséquence directe et prouvée par audit : un helper de test hors `ImagesPage` (`test_inference_page.py::_images_page_paths()`) lisait encore `item.text()` comme chemin complet — migré vers `item.data(Qt.UserRole)`, sans aucun changement du comportement Inference lui-même (voir `docs/missions/MISSION_019.md`).
- **Traitement de "Run" sans cible fonctionnelle légitime (Mission 020)** : confirmé par audit répété (Missions 018, 019 et 020) qu'aucun lancement générique n'existe dans le projet — `InferencePage.generate_button` est une action contextuelle à une page précise, pas un point d'entrée adapté à une barre d'outils toujours visible. Retenu : même traitement que `DashboardPage.trainingButton` (Mission 017) — action visible, `setEnabled(False)`, tooltip explicite, sans handler ni sémantique inventée. Ce même précédent guide désormais deux décisions de missions différentes (017 et 020), confirmant sa validité comme convention du projet pour toute action UI sans cible fonctionnelle réelle.
- **Séparation transport / rôle / usage-workflow pour les images de référence (Mission 021)** : avant de concevoir toute orchestration multi-image, trois responsabilités distinctes ont été identifiées et volontairement découplées — le transport (envoyer physiquement un fichier au moteur, seul sujet de Mission 021), le rôle sémantique (à quoi sert l'image — identité, vêtement, décor, pose... — non implémenté), et l'usage moteur/workflow (img2img, IP-Adapter, ControlNet, LoadImage... — non implémenté). `ComfyUIEngine.upload_image()` reste strictement une primitive de transport : elle ne connaît ni rôle ni mécanisme moteur, et ne conserve aucun état d'upload sur `self`, ce qui la rend appelable N fois de façon totalement indépendante sans qu'aucune modification d'elle-même ne soit nécessaire pour un futur besoin multi-image. `type` n'est délibérément pas exposé en paramètre (toujours `"input"`, seule valeur utile à un futur `LoadImage`) — extension additive possible plus tard si un besoin réel de `"output"`/`"temp"` apparaît, même logique que l'ajout de `checkpoint_name` à `generate_image()` en Mission 013. Retour `dict` (pas de nouveau Domain/dataclass) : reflet direct de la réponse ComfyUI, cohérent avec `wait_for_result()` qui retourne déjà un `dict` brut sans retravail. Aucune méthode batch (`upload_images()`) créée : le protocole ComfyUI vérifié n'expose qu'un endpoint unitaire, un fichier par requête.
- **Représentation 0..N verrouillée dès la frontière applicative (Mission 022)** : bien que l'UI de Mission 022 ne permette de sélectionner qu'une seule image, la frontière `InferencePage → GenerationWorker → GenerationManager` utilise dès à présent une collection (`reference_images: list[str]`), jamais un singleton `reference_image`/`reference_image_path` — décision explicitement verrouillée par l'architecte pour ne jamais avoir à migrer un design singulier vers pluriel plus tard. Le scalaire `Optional[str]` ne vit qu'à l'intérieur de `InferencePage` (seul endroit où l'UI limite réellement à 0/1) ; la conversion en liste a lieu à un unique point (`_start_generation()`). Aucun rôle, aucun dictionnaire `role → image`, aucune taxonomie créés — reportés à une future mission avec un besoin réel démontré.
- **Snapshot défensif contre les changements de sélection UI pendant l'exécution (Mission 022)** : `GenerationWorker.__init__()` copie la liste `reference_images` reçue (`list(reference_images)`, jamais la référence à l'objet de l'appelant) et la capture avant `moveToThread()`/`thread.start()` — reproduit exactement le mécanisme déjà éprouvé pour `prompt_text`/`output_directory`/`_generation_workspace_root`. Propriété vérifiée explicitement par test (mutation de la liste de l'appelant après construction du worker, snapshot transmis à `generate()` prouvé inchangé).
- **Fail-fast pour les échecs d'upload de référence (Mission 022)** : les appels `upload_image()` sont placés dans le même bloc `try` que `generate_image()` dans `GenerationManager.generate()`, réutilisant sans duplication la normalisation d'erreur déjà existante (`ComfyUIEngineError`/`OSError` → `GenerationError`). Le premier échec interrompt immédiatement la boucle — `generate_image()` n'est jamais atteinte si un upload échoue, y compris au milieu d'une liste de plusieurs références.
- **Séparation construction des workflows / transport HTTP (Mission 023)** : toute la connaissance du graphe ComfyUI (node IDs, `class_type`, connexions) vivait dans une seule fonction d'un seul fichier (`comfyui_engine.py`), acceptable avec un seul graphe possible mais plus dès qu'un deuxième doit coexister sans se mélanger. Retenu : `src/engines/workflows/comfyui_workflows.py`, fonctions pures `dict → dict` uniquement — explicitement **aucune** classe abstraite `Workflow`, registry, plugin system ou DSL, une abstraction plus riche n'étant justifiée par aucun besoin concret au-delà de deux graphes. `_submit_and_download()` (nouvelle méthode privée de `ComfyUIEngine`) factorise la séquence `submit → wait_for_result → download_output` déjà existante, elle-même volontairement agnostique de tout graphe.
- **Valeur `DEFAULT_IMG2IMG_DENOISE = 0.75` (Mission 023)** : centralisée dans un seul endroit (`comfyui_workflows.py`), jamais dupliquée, jamais exposée au-delà de `build_img2img_workflow()` — ni par `ComfyUIEngine.generate_image()`, ni par `GenerationManager.generate()`, ni par `InferencePage`. Choisie comme compromis communément documenté par la communauté ComfyUI. **Observation empirique du smoke test réel (voir `docs/missions/MISSION_023.md`)** : l'équilibre référence/prompt obtenu à `0.75` dépend fortement de la proximité sémantique entre le prompt et le contenu de la référence, et du checkpoint utilisé (SD1.5 de base ici) — un prompt proche de la référence peut laisser la référence dominer visuellement, un prompt contradictoire fait nettement ressortir l'influence du prompt. Ce comportement est cohérent avec le mécanisme `denoise` lui-même, pas un défaut de câblage (vérifié point par point pendant le smoke test). Aucun réglage exposé à l'utilisateur cette mission — voir besoin futur "réglage de force img2img/denoise" ci-dessous.
- **Rejet explicite de plus d'une référence, sans retrait de l'architecture 0..N (Mission 023)** : ce workflow img2img simple ne peut structurellement utiliser qu'une seule image d'entrée (`VAEEncode` prend un seul `LoadImage`). `GenerationManager.generate()` lève `GenerationError` si `len(reference_images) > 1`, **avant tout appel `upload_image()`** — jamais un `reference_images[0]` silencieux. `reference_images` reste un `list[str]` à toutes les frontières inter-couches ; seule la capacité de *ce* workflow particulier est limitée à 1, pas la forme du paramètre — un futur workflow multi-référence lèverait cette limite sans changer `reference_images` ailleurs.
- **Frontière opaque `upload_image()` → workflow (Mission 023)** : `GenerationManager` conserve le `dict` `{"name", "subfolder", "type"}` retourné par `upload_image()` dans une variable locale transitoire, sans jamais en inspecter les clés, et le transmet tel quel à `ComfyUIEngine.generate_image(reference_image=...)`. Seule `build_img2img_workflow()` (via `_load_image_input()`) sait le traduire en input `LoadImage` (`"subfolder/name"` ou `name` selon la présence d'un sous-dossier) — vérifié par test dédié que `GenerationManager` ne référence aucun terme du vocabulaire JSON ComfyUI (`LoadImage`, `VAEEncode`, `class_type`...).
- **Frontière générique/ComfyUI pour le nom du paramètre de force (Mission 024)** : le concept reste générique (`reference_strength`, `float`) dans `InferencePage`/`GenerationWorker`/`GenerationManager` ; il ne devient `denoise` (vocabulaire natif ComfyUI) qu'à l'unique appel `GenerationManager.generate()` → `ComfyUIEngine.generate_image(denoise=...)` — la même classe qui manipule déjà `checkpoint_name`. `GenerationManager` ne transmet `denoise=` que si une référence est présente **et** qu'une valeur a été fournie (`extra_kwargs` conditionnel) ; sinon `ComfyUIEngine.generate_image()`/`build_img2img_workflow()` retombent sur leur propre défaut existant (`DEFAULT_IMG2IMG_DENOISE`) — garantie structurelle, pas conventionnelle, que le comportement historique Mission 023 reste inchangé pour un utilisateur qui ne touche jamais au slider. Vérifié par test architectural dédié (aucun `"denoise"` dans la source d'`inference_page.py`).
- **Reset du slider intégré au point de reset déjà existant (Mission 024)** : plutôt que dupliquer la logique dans `_on_remove_reference_clicked()` et `reset_for_workspace_change()`, le reset (valeur `75`/désactivation) est ajouté à `_clear_reference_selection()`, déjà le point de reset unique partagé par ces deux appelants depuis Mission 022 — même principe de non-duplication déjà appliqué à la sélection de référence elle-même.

## Dépendances importantes

`requirements.txt` : `PySide6`, `pydantic`, `opencv-python`, `numpy`, `pillow`. Tests : stdlib `unittest` uniquement. Aucune dépendance ajoutée pour la résolution de répertoire Application Settings (Python standard `os`/`pathlib` uniquement, décision explicite de ne pas utiliser `QStandardPaths` ni `platformdirs`/`appdirs` pour garder Infrastructure indépendante de Qt).
